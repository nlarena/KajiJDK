# Upgrades to the JIT and to how we measure it, read from the papers — 2

Five papers read on 2026-10-06 against the state of `src/burst/` and `bench/`, with the concrete
change each one suggests and where it lands. Written after a first attempt to measure our engine
against HotSpot came out **unusable** — the dispersion was 32–94% where this box's documented noise
ceiling is ±12% — so the order below is not by depth but by what unblocks that measurement.

Provenance: the five below were downloaded and read (`papers/pdf/`, text in `papers/txt/`). A sixth,
**Gal, Probst, Franz, _HotpathVM_ (VEE 2006)**, could not be fetched: the author's copy at
`ics.uci.edu` now returns an HTML landing page and the ACM copy is paywalled. What this note says
about it comes from its abstract and secondary sources, so it is weaker evidence than the rest and is
kept out of the ordered list.

## 1 · Warmup: the assumption our harness is built on is probably false

**What it does.** Runs microbenchmarks for **2000 in-process iterations across 30 fresh process
executions**, under a purpose-built runner (Krun) that reboots the machine before each process
execution, stops network cards and userland daemons, and waits for a consistent temperature. Then it
classifies each time series automatically with **changepoint analysis** instead of eyeballing it, into
**warmup**, **slowdown** or **flat**.

**The result that matters to us.** Only **30.0–43.5%** of ⟨VM, benchmark⟩ pairs consistently reach a
steady state of peak performance, depending on machine and OS, and **none of the seven VMs** they
studied did so consistently. Some benchmarks get *slower* over iterations. Their conclusion is blunt:
benchmarking that assumes a steady state "is likely to be partly or wholly misleading", and
ineffective or harmful optimizations may have been accepted on that basis.

**What our harness does today.** `bench/hs/medir.py` measures the same workload at N and 2N
repetitions and takes the slope, so that start-up cancels exactly. That part is sound. But it then
assumes the slope *is* steady-state performance, which is precisely Hypothesis H1 — the one this paper
tests and finds false more often than not. If HotSpot has not reached peak by our calibrated N, its
slope is **pessimistic** and our ratio flatters us.

**The change.** Report the per-iteration time series, not one slope: run K in-process iterations and
emit all K, then classify with changepoint analysis before computing anything. Until a run is
classified **flat** or **warmup-then-flat**, no ratio against HotSpot should be quoted. This is the
first thing to build, because every number downstream depends on it.

## 2 · Statistical rigor: our ±12% threshold is a heuristic, not an interval

**What it does.** Surveys 50 Java performance papers and finds that **16 of 50 do not state their
methodology at all**, and that the prevalent data analyses — report the best of N (which is what the
SPEC run rules ask for), the worst, or the mean — are not statistically rigorous. Its illustrative
case: with *best of 30*, two garbage collectors look equal and a third looks like a clear winner; with
**95% confidence intervals**, the first comparison is a real difference and the second one is noise,
because the intervals overlap.

**Its two prescriptions**, which are different measurements and not interchangeable:

- **Start-up**: many measurements, each one VM invocation running a **single** iteration; confidence
  intervals across them.
- **Steady state**: many measurements, each one VM invocation running **many** iterations; keep only
  the iterations after start-up; intervals across (iterations × invocations).

And `JavaStats`, which monitors the observed variability to decide **how many measurements are needed**
for a target interval width, instead of fixing the count in advance.

**What we do today.** `bench/BASELINE.tsv` reads differences against a **±12% threshold** that is
honestly labelled as the measured layout-noise ceiling of this box. That is better than nothing and
better than most of the 50 papers, but it is a single scalar standing in for an interval, and it is
inherited across runs even though the file itself warns that the floor depends on what the machine is
doing.

**The change.** Replace the fixed repetition count with the `JavaStats` rule — keep sampling until the
confidence interval is narrower than the effect being claimed — and report intervals instead of a
threshold. Note the ordering: **Barrett supersedes this paper where they disagree**, and says so
explicitly, that simple heuristics of the Georges kind are not sufficient to decide that a steady
state was reached. Use Georges for *how many samples and how to report them*, Barrett for *whether the
samples mean anything*.

## 3 · Copy-and-patch: the family our emitter already belongs to

**What it does.** Builds code at run time by stitching together **binary stencils** — pre-built
implementations of an AST node or a bytecode opcode with holes where immediates, stack-slot offsets and
branch targets get patched in. No intermediate representation, no optimization passes. Against Liftoff,
the baseline tier in Chrome, their WebAssembly compiler has **6.5× lower start-up delay while
generating 63% better code**; against interpreters, execution is an order of magnitude faster at
negligible start-up cost.

**What `burst` does today.** A hand-written x86-64 emitter in a single pass over the bytecode, with
inline caching and stack caching (Hito F2) and superinstructions deliberately skipped. That *is* a
template JIT, written without the name — so this paper is the measured ceiling of the approach we
already took, which makes it the right thing to read before replacing anything.

**The change.** Not a rewrite. Two things the paper makes concrete and that our emitter does not do:
pre-building the stencils **offline** from compiled C, instead of hand-writing each emission, and
**composing** variants per operand shape (register vs immediate vs spilled) so the common shape pays no
dispatch. Both are incremental and both are measurable against the current census of 5083 methods.

## 4 · The client compiler: the blueprint if there is ever a second tier

**What it does.** Describes C1 as redesigned for Java 6: a high-level IR in **SSA form** built by
abstract interpretation of the bytecode, lowered to a machine-like LIR, with **global** register
allocation by linear scan. Before Java 6 the IR was not in SSA and global optimizations were not
possible; the redesign is what enabled them.

**Why it is relevant and why it is not urgent.** This is the compiler we are measuring ourselves
against on the *first* tier, written by the people who also wrote the allocator below. It is the right
design to copy **if** the measurement says the loss is in register pressure and in missing global
optimizations. It is the wrong thing to start if the loss turns out to be elsewhere — which is exactly
what we cannot say yet.

## 5 · Linear scan: the piece a template emitter structurally lacks

**What it does.** The register allocator of that client compiler. Over basic linear scan it adds
**lifetime holes**, **interval splitting** when register pressure is too high, **use positions** to
decide which interval to spill, and **fixed intervals** to model machine constraints. Three further
optimizations need no data-flow analysis: optimal split positions (moved out of loops), register hints
to remove register-to-register moves, and spill-store elimination.

**The measured trade.** At **compilation speed equal to** the old local allocator of JDK 5.0, integer
benchmarks run about **15% faster**. And the number that frames the whole decision: the server compiler
produces faster code at **more than ten times** the compilation time, which is why the client compiler
does not use it.

**What this says about us.** A template emitter assigns registers locally by construction; it has no
notion of a lifetime interval. That 15% is therefore a reasonable estimate of what a global allocator
would buy on top of our current emission — useful precisely because it is *small*, which means it is
not where a two-orders-of-magnitude gap lives.

## Suggested order

1. **The warmup classification** (§1). Without it there is no trustworthy ratio against HotSpot, and
   every decision below is taken blind.
2. **Confidence intervals in `bench/`** (§2), replacing the ±12% scalar. Cheap, and it makes the
   existing baseline able to detect a regression instead of a large change.
3. **Re-measure against HotSpot on a quiet machine**, and only then decide. The first attempt had a
   competing `java` process with 83,000 s of accumulated CPU; that alone explains the 94% dispersion.
4. **Stencils and operand-shape variants** (§3), which is the cheapest engine work and stays inside
   the design we already have.
5. **Global register allocation** (§5), worth about 15% on the published evidence — so it is a
   late-stage item, not a first move.
6. **An SSA tier** (§4) only if the measurement points there.

The rule the bench already applies stays: a change that does not move the measured number, measured with
intervals and on a classified-steady series, does not go in.

## The one that could not be downloaded

**HotpathVM** (VEE 2006) is the closest in spirit to our situation: a trace JIT for a JVM in **150 KB**
of code and data that, per its abstract, "in some cases rivals heavy-weight just-in-time compilers". It
identifies traces of hot bytecode spanning several basic blocks and methods and compiles them by SSA
construction, hoisting across trace side-exits without compensation code. If a copy turns up it belongs
in this list, because "small JIT that punches above its weight" is the exact shape of this project — but
nothing above should be decided on an abstract.
