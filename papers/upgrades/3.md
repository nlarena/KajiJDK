# Upgrades to the JIT, read from the papers — 3: inlining

Three papers read on 2026-10-06, chosen **by a measurement and not by taste**. The profile against
HotSpot (see the JIT milestone in `docs/roadmap.md`) says the gap is inlining, so this note is about
inlining and nothing else.

What the profile says, because it is what makes this list the right list:

| dimension | ours / HotSpot | Tukey interval |
|---|---:|---|
| arithmetic on locals | 2.78× | 2.27 – 3.41 |
| `putfield` of a reference | ~4.9× | (no interval yet) |
| `aastore` | ~4.3× | (no interval yet) |
| **monomorphic interface dispatch** | **8.70×** | 7.53 – 10.04 |
| **megamorphic interface dispatch** | **0.45×** | 0.40 – 0.51 |

HotSpot costs **0.93 ns per inner iteration** on the monomorphic row — less than a call, so C2 inlines
the call away and then optimizes the body. Going megamorphic it loses ~18× and **we win by 2.2×**. So
where we lose 8.7× we are not competing against better dispatch, we are competing against *no
dispatch*; and the moment inlining stops being available, the comparison inverts. Nothing in
`papers/upgrades/2.md` is the right size for that gap: global register allocation is worth ~15% by
Wimmer's own numbers, and copy-and-patch is about compile speed, not about removing calls.

Algorithm for Just-in-Time Compilers_ (CGO 2019)**, has no freely downloadable copy; what this note

## 1 · Type feedback: the PIC we already have is the input

**What it does.** Extract the receiver types the program actually saw and feed them back to the
compiler, which can then inline **any** dynamically-dispatched call: the call becomes a class
comparison plus the inlined body, with the original dispatch kept in the `else` branch for everything
else. On large SELF programs it cut call frequency by **3.6×** and improved performance by **1.7×**.

**Why this paper and not another.** Its sentence about the source of the type profile is, word for
word, our situation: *in SELF no additional mechanism is needed to record receiver types, since the
system already uses polymorphic inline caches to speed up dynamic dispatch*. We have had a PIC since
Hito F2, and today it is used **only to pick the target**. The data for the optimization the profile
asks for is already being collected and thrown away.

**Their policy, which is smaller than I expected.** The SELF compiler uses *simple rules*: inline if
the method is small and if the estimated size of the caller, including everything inlined so far, is
not too big — the second condition is what stops a cascade of small methods. And they do **not** inline
highly polymorphic sends: five or more receiver types and the call stays a call.

**The number that warns us.** For the sends that are *not* inlined, type feedback pushes the median
number of type tests per send **up**, from 1.35 to 1.7. Not because the program became more
polymorphic, but because inlining removes the easy sends and what remains is skewed towards the hard
ones. Read against our profile, that is precisely the risk: **inlining would erode the megamorphic row
where we currently win 2.2×**, because a failed guard costs a deopt where today we pay a cheap PIC.
The policy has to decide when *not* to inline, and that decision is the whole game.

## 2 · Dynamic deoptimization: the safety net speculation needs

**What it does.** Lets optimized code be turned back into unoptimized code **on demand**, so the
source-level state can be reconstructed. The key design element is **interrupt points**: optimized code
can only be suspended at relatively widely spaced points, and at each one the state is recoverable —
which lets the compiler optimize freely *between* those points. Deoptimization affects only the
activations involved; everything else keeps running at full speed.

**What we have.** `burst` already deopts: there are resume sites, a deopt stub emitted only when
something can deopt, and tests covering division by zero, a callee without code, a PIC that does not
know the receiver, and an insufficient frame budget. So this is not a build-from-zero; it is the paper
to check our design against before adding *speculative* inlining, which multiplies both the number of
deopt sites and the amount of state each one must restore.

**The caveat we should copy.** They are explicit that the SELF compiler **does not perform certain
optimizations** in order to keep full debuggability. There is a price, and they name it instead of
hiding it.

## 3 · The empirical study: a policy sized for one tier

**What it does.** An online-profile-directed inlining strategy, evaluated for **both performance and
compilation overhead** — the second half matters for us as much as the first, since we have a single
tier and anything we spend compiling is paid on the spot. They rely **solely on profile information**
for which methods to inline along which paths; the only static heuristic they keep is *always inline
very small methods*. Call-site distribution and invocation frequency are collected with dynamically
generated instrumentation.

**The result worth copying first.** Their **tiny-only** policy — inline nothing but the very small
methods — has *very little impact on compilation time, as expected, while producing significant
performance improvements* over not inlining. That is the cheapest possible first step and it is
measured, not assumed. Their profile-directed policies go further but are not uniformly better:
`compress` **degrades** with profile-based inlining and `mtrt` shows no significant improvement, which
is the kind of honesty our bench already demands of itself.

## Suggested order

1. **Tiny-only inlining**, no type feedback, no speculation. Smallest possible change, measured
   against the five dimensions we now have. If it does not move the monomorphic row, nothing more
   elaborate will.
2. **Type feedback from the existing PIC** (§1): the receiver types are already recorded; add the
   guard-plus-inlined-body shape with the original dispatch in the `else`.
3. **A "do not inline" rule** before widening anything: five or more receiver types stays a call, which
   is SELF's own cutoff and the one that protects the megamorphic row where we currently win.
4. **Re-measure the whole profile**, not just the monomorphic row. The specific thing to watch is
   whether the megamorphic 0.45× degrades — that is the predicted cost, and if it appears, the policy
   is wrong rather than the idea.
5. Only then look at the Graal algorithm, which alternates inlining with optimization passes — and a
   template emitter has no passes to alternate with, so it probably does not apply to us as built.

The rule the bench exists to apply still holds: a change that does not move the measured number, with
intervals and on a classified-steady series, does not go in.
